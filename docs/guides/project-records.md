# 项目记录填写规范

此规范服务于个人学习与实践记录。项目列表帮助选择，项目详情解释全貌，阶段记录保留变化。沿用现有全站容器、字体、圆角、按钮和响应式断点；增加内容时不重新设计一套页面。

## 三个展示位置

| 位置 | 填什么 | 数据来源 |
| --- | --- | --- |
| 项目卡片 | 名称、副标题、一句话用途、当前阶段、实践重点、最近进展 | 项目字段 |
| 最近的实践记录 | 日期、项目、记录类型、标题、摘要，最多五条 | 各项目 journal 自动汇总 |
| 项目详情 | 为什么做、当前能力、我的参与与 AI 协作、关键选择、推进路径、阶段记录、验证、复盘、下一步、实现方式及关联内容 | 同一项目档案 |

填写入口为 `src/features/work/entries.js` 的 `workEntries`。纯方案探索保存在 `design-projects.js`；变成实际开发项目时移入 entries，保留 id，避免维护两份。

## 一份项目档案

基础必填：`id`（英文短横线，发布后保持不变）、`title`、`subtitle`、`kind`、`publication`、`statusLabel`、`date`（YYYY-MM-DD）、`time`、`summary`、`practiceFocus`、`latestUpdate`。

正文建议依次回答：

1. `problem`：什么具体场景促使你做这个项目？
2. `solution`：现在采用什么办法？
3. `modules`：核心能力，每项 `[名称, 简短说明]`，通常 3–4 项。
4. `role` 与 `aiCollaboration`：自己决定和推进的部分、AI 协助的部分。没有 AI 协作可以不填。
5. `keyDecisions`：2–3 个选择，以及原因或取舍。
6. `flow`、`challenge`：推进路径与真正遇到的卡点。
7. `validation`、`result`：怎么检查、看到什么、哪些还没验证。
8. `whatILearned`、`nextSteps`：现在的认识与接下来准备验证的事。
9. `technologies`：简要实现方式，不要求堆满技术名词。

数组字段可为空数组，可选正文也可以留空；详情会自动隐藏没有内容的模块和对应目录，不显示占位空框。暂未形成结论时也可写清当前问题，不编造成绩。`journal: []` 表示采用项目记录模板，但暂时不展示阶段记录区。

可选材料：`repoUrl`、`screenshot`、`coverCaption`、`relatedTopics` / `relatedNotes` / `relatedTools`（已有内容 ID）。图片要注明是实际截图、历史存档还是设计方案；没有截图可用 `visualPaths: [[路径名, 说明], ...]`、`visualOutcome` 和 `coverCaption` 生成轻量流程图。没有真实可用的体验或仓库链接就留空。

## 一条阶段记录

在对应项目的 `journal` 中添加：

```js
{
  id: 'first-device-check',
  date: '2026-09-12',
  type: '验证记录', // 也可以是阶段思考、关键选择、功能迭代
  title: '这次主要解决了什么问题',
  summary: '一句话说明变化，供列表浏览。',
  goal: '当时希望解决什么？',
  action: '实际做了哪些调整？',
  evidence: '怎样验证？证据来自哪里？',
  reflection: '有什么新认识？还存在什么边界？'
}
```

最近列表自动按日期倒序显示，同日期按数据中的顺序。点击进入 `#/projects/项目ID?record=记录ID`，详情自动展开并定位。返回列表继续原位置；从其他栏目重新进入项目页则从首屏开始。记录 ID 只用英文字母、数字和短横线，避免改名破坏旧链接；同一项目内不重复。

## 内容准确性

- `publication: 'published'` 仅表示在网站公开展示，不代表产品已上线；产品阶段由 `statusLabel` 和正文说明。
- 代码存在、测试通过、真实调用成功、真机验收、上线发布是不同的结果。
- 转述项目状态文档时写出日期与来源，不描述为本轮亲自复测。
- 一次灰度成图成功不能推导为全场景可用。
- 不把环境变量、密钥、内部服务标识等私人配置放进公开内容。

新增后运行 `npm run check` 和 `npm test`，并实际检查卡片、详情、记录定位以及手机宽度排版。
